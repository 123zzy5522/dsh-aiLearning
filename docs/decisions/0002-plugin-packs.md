# 0002. 能力做成插件包，而不是写进内核

- 状态：已采纳
- 日期：2026-10-21
- 相关：[#6](https://github.com/123zzy5522/dsh-aiLearning/pull/6)、`host/capabilities.js`、`plugins/`

## 背景

三种学习模式（从零学 / 复习 / 快速过）最初的可选实现是“三个 DSH 预设”，即 `cordis.patch.yml` 里三条 preset 行。

评估后发现：

- DSH 的 preset 在会话创建时固化，`recompose` 只允许“尚未产出任何内容”的空白会话，**中途换模式必须新开会话**。
- preset 列表会随模式数量膨胀，用户要在新建会话时选对预设。
- 每加一个模式都要改 `cordis.patch.yml`，内核文件为插件数量而改。

同时，“加一个插件就多一种能力”是明确的产品方向（未来还有绘图理解、题库、导出）。

## 选项

| 选项 | 好处 | 代价 |
|---|---|---|
| 一模式一预设 | 工具集物理隔离，第一轮提示词就正确 | 预设列表膨胀；不能中途换；每模式改内核配置 |
| 模式写进内核代码 | 实现最快 | 每加模式改内核；无法第三方扩展 |
| **能力注册表 + 插件包** | 加目录即加能力；可第三方 | 工具集是并集，靠运行时门禁而非物理隔离 |
| 进程外插件（子进程/MCP） | 最强隔离 | 复杂度高；当前没有这种需求 |

## 决定

内核提供**能力注册表**（`host/capabilities.js`），模式是 `plugins/<id>/` 下的一个包，通过 `plugin.json` 声明、`host.js` 提供 `mode.rules`。

仍然是**单一预设**，模式通过 `learn_status` 返回的 `modeRules` 生效。

## 理由

- 加一个模式 = 加一个目录，内核零改动，`cordis.patch.yml` 也不动。
- 模式是“教法”而不是“工具体系”，三个内置模式用同一套工具，差别全在规则文本。
- 坏插件只记录不致命，第三方包写错不会让课本打不开。

## 后果

- **好**：扩展成本低；模式可按书切换；`/build` 的 `packs.failed` 让加载问题可见。
- **不好**：
  - 工具集是并集：任何模式都能看到全部 `learn_*` 工具，靠 `mode.tools` 的约定约束，不是物理隔离。
  - 教法以提示词形式生效，模型仍可能不完全遵守——没有硬门禁。
  - 插件目前只能从仓库内 `plugins/` 加载，还不能从 npm 装（`kind: "ingest"` 同理）。
- **重新考虑的信号**：如果某个模式需要“第 0 轮就不同的系统提示词”或完全不同的一组工具，就为它生成独立 preset，而不是继续堆 `modeRules`。
